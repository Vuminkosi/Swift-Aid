## Contract requirements for future additions

Use typed request/result/error models, cancellation, explicit pagination/filter bounds, capability responses, version or idempotency semantics where the authoritative backend supports them, and retry rules that distinguish retryable transport failure from authorization denial/conflict. Keep presentation state outside transport and persistence. Use fake adapters only through the explicit `SwiftAid:UseFakeServices` composition gate: Gateway requires Development/Test and the flag; Mobile compiles the gate under DEBUG and requires the flag. Do not create fake-specific product UI; normal shared screens consume the selected contract implementation. Where wire behavior is absent, mark it **Muse contract required** and have Muse approve the endpoint/schema before implementing a real adapter.

The backend remains PostgreSQL-authoritative; Qdrant is not a case database. Public intake does not confer organizational membership or managed-case access.

## Observed typed request and response shapes

These fields are transcribed from current Contracts source, not a proposal for absent endpoints:

- `ICaseQueueClient.GetMineAsync(limit, cancellationToken)` returns `CaseQueueResult(Access, Items)`; each `CaseQueueItem` contains case ID, workflow, country code, accountable owner actor ID, aggregate version and update time. It is a minimum-routing projection, not report content.
- `ICaseTimelineClient.GetAsync(caseId, limit, cancellationToken)` returns `CaseTimelineResult(Access, Timeline)`. The timeline includes a minimum case header and oldest-first immutable entries with event kind, schema/version and actor/time metadata; reasons and report content remain sealed.
- `ICaseCommandClient.SendAsync(caseId, CaseCommandInput, cancellationToken)` returns `CaseCommandResult(Status, CommandId, EventIds, AggregateVersion, ReportRevision)`. Input includes command type, reason, optional expected version, and command-specific fields. The server replaces the optional expected version with its authoritative timeline version before dispatch; conflict and idempotent replay behavior come from the existing API contract.
- `IIntakeCoordinationClient.GetQueueAsync(routingStatus, limit, cancellationToken)` returns access plus redacted `IntakeCoordinationQueueEntry` rows; detail includes action history; queue options describe configured currently eligible routes. `ActAsync` carries receipt ID, expected version, action, optional target queue and reason. The API rejects unknown JSON fields and maps conflicts/invalid/unavailable explicitly.
- `IGuestIntakeTransport` creates a session from session ID and receipt proof, submits a typed `IntakeSubmission` with session capability and receipt proof, reads a receipt with proof, and reads public intake metadata/country catalogue. Local `GuestSubmissionLocalState` values Draft/Queued/NeedsAttention are not server outcomes; `Received` requires an actual `IntakeReceipt` response. Secrets/proofs must remain outside UI projections/logs. The local original-audio record remains `LocalOnly`; no guest-media upload endpoint exists.

For detail shapes and validation bounds, the authoritative definitions are `src/SwiftAid.Contracts/Cases/CaseQueue.cs`, `CaseTimeline.cs`, `CaseCommands.cs`, `src/SwiftAid.Contracts/Intake/IntakeCoordination.cs`, `src/SwiftAid.Client/Intake/GuestSubmission.cs`, and corresponding Gateway endpoint implementations. Session command records are in `src/SwiftAid.Contracts/Sessions/CommunitySessionContracts.cs`. Read those definitions before changing adapters; this table is intentionally not a replacement schema.


## Typed presentation and client contracts

`UiCapabilityResult<T>` carries a result code and metadata including contract version, provenance, timestamp, availability and notice. `PageRequest` defaults to page 1/25 and bounds size to 1-100. Organization, investigation and work-management interfaces now exist in `src/SwiftAid.Client/Presentation/`; they are frontend contracts, not evidence of matching live endpoints. Organization and investigation mutation methods currently lack an expected-version argument; investigation snapshots expose a version but do not send it back on commands. Work-management commands include `ExpectedVersion` and validate action-specific payloads, but `IWorkManagementClient` is registered only to `FakeWorkManagementClient` in each host fake-services branch; normal composition does not register a client, and source describes the interface as local practice operations. None of these shapes should be treated as approved backend wire schemas without Muse review.

`IPublicCommunitySessionClient` is the shared typed public contract used by Gateway and Mobile session pages; its configured implementation varies by host/composition. `IUiDemoJourneyClient` is legacy scenario scaffolding and no route page injection was found; it is not a product screen or acceptance journey.

Host composition is controlled by `SwiftAid:UseFakeServices`. Gateway enables fake clients only in Development/Test when the flag is true; Mobile compiles the fake branch only under DEBUG and requires the same flag. Otherwise missing capabilities use unavailable adapters. Route pages inject the ordinary service contracts. Fake adapters remain composition-only; the target removes visible Sample data badges without replacement; internal fake configuration and the safely isolated fake store remain unchanged.

## Shared presentation and platform-specific adapters

The approved architecture centralizes reusable page/UI, shared presentation state and contracts so web and Android do not reimplement workflows independently. `SwiftAid.UI` is the approved owner for shared pages/components; `MudHidden` is the approved mechanism for responsive desktop/mobile variants against the same state. Current shared `MudHidden` surfaces include `PublicReportSurface`, `OperationsDashboard`, `OperationsCaseQueue`, and `OperationsMonitoringQueue`. Gateway routes call these surfaces at `/report`, `/dashboard`, `/my-cases`, `/assignments`, `/monitoring`, `/follow-ups`, and `/escalations`; Mobile GuestReport also calls `PublicReportSurface`. `PublicHomeSurface` is referenced by the Mobile Home route only; Gateway does not yet host that shared page. `SwiftAidApplicationShell` is referenced by Mobile `MainLayout` only. These component and route references establish source wiring, not verified rendering or full workflow parity. Each host supplies native/browser adapters through its own DI. Existing host-local pages remain implementation evidence while migration proceeds; do not describe migration as complete or fork state logic to bridge it.

`PublicReportSurface.InitialSubmission` is declared but is not forwarded to the desktop `PublicReportForm` or mobile `GuidedReportStepper`. Both host callers bind the shared `Draft` parameter typed as `PublicReportDraft`; persistence remains host-specific through callbacks/adapters, and Mobile GuestReport supplies `OnSaveMobileDraft`. Mobile passes `InitialSubmission`, but `PublicReportSurface` does not forward it to either responsive child. Initial-submission hydration through this surface is therefore not evidenced and the declared parameter currently has no observed effect. Verify this state contract before relying on it.

Observed host adapters: Gateway `Program.cs` has separate fake and normal compositions; fake intake/case/session clients are gated by Development/Test plus `SwiftAid:UseFakeServices`, while normal composition binds server-backed API clients. Mobile binds authentication/session, encrypted guest stores, guest intake, case/monitoring/session/notification clients; check the exact current `MauiProgram` registration before assuming a service exists (`ICaseQueueClient` is registered in Mobile fake composition only; no normal Mobile queue-client registration was found). Android builds register `IAudioCaptureService` and `IAudioPlaybackService` to `AndroidAudioCaptureService`; other targets use `UnsupportedMobileAudioCaptureService`. `IGuestAudioStore` uses `EncryptedGuestAudioStore`. No guest-media upload endpoint is evidenced.
